## 任务 0：换一个稳定的 TTS 模型（先做，避免后面一直 429）

**上下文**：
- 当前 `.env` 里用的 `tts-1` 模型一直 HTTP 429，每句话耗时 8 秒左右，全是在白等重试。
- 上一轮探测到的可用模型清单里有 `qwen3-tts-flash`、`speech-1.5`、`speech-1.6`、`tts-1-hd`，可以试试这些。

**步骤**：
1. 在外面的终端（**不是沙箱**，需要联网）运行：
   ```bash
   cd /Users/hancg/Desktop/hackathon/voice_relay
   python3 try_alt_tts.py qwen3-tts-flash
   ```
   它会尝试用 `qwen3-tts-flash` 合成一句中文，保存为 `alt_tts_qwen3-tts-flash.wav`。

2. 用 `afplay alt_tts_qwen3-tts-flash.wav` 播放，确认是清晰的中文女声。

3. 如果 `qwen3-tts-flash` 不行（HTTP 429 或其他错误），依次试 `speech-1.5`、`speech-1.6`、`tts-1-hd`：
   ```bash
   python3 try_alt_tts.py speech-1.5
   python3 try_alt_tts.py tts-1-hd alloy   # tts-1-hd 可能需要指定音色
   ```

4. 找到一个能成功、音质可接受的模型后，编辑 `.env` 文件：
   ```bash
   # 例如用 qwen3-tts-flash
   TTS_MODEL=qwen3-tts-flash
   ```
   保存，然后重启 `server.py`（如果在运行的话，Ctrl-C 停掉，再 `python3 server.py` 重新启动）。

5. 重新运行端到端自检 `./e2e_check.sh`，看 TTS 耗时是否降下来了。把第 2 句和第 3 句对应的终端 A 日志里的 `[Time]` 行贴给我。

**预期**：
- 如果换的模型稳定，`[Time]` 行里 TTS 耗时应该降到 1-3 秒（而不是 8 秒），ASR 耗时也会降（因为不重试了）。
- 如果换了还是 429，说明整个 API 通道都在限流，要考虑换密钥或者降级到纯离线语音（演示时只用板子自带的蜂鸣音）。

## 任务 1：烧录固件

**前置条件**：
- ESP32-S3 开发板通过 **数据线**（不是只能充电的线）插在电脑上，插板子**左边那个口**（CH9102F）。
- 板子上电（插上去通常就会自己上电）。
- 运行 `ls -l /dev/cu.*`，应该能看到 `/dev/cu.usbmodem*` 设备。如果看不到，检查线和接口。

**步骤**：
```bash
cd /Users/hancg/Desktop/hackathon
./flash.sh
```

**它会做三件事**：
1. 编译（已经编译过的话会很快，显示 `Sketch uses 2743427 bytes (65%)`）。
2. **校验当前启动分区**（只读，不写 Flash）—— 确认板子启动的是 ota_1。
3. **烧录到 0x730000**（写 ota_1）—— 约 2.6 MB。
4. 抓 8 秒启动日志。

**预期输出**：
- `== 校验启动分区 (只读) ==` 下面应显示 `启动分区: ota_1 (Wake)  OK`（这是我从 `flash.sh` 里看到的文案）。
- 烧录阶段有进度条，写完有校验消息（我没见过实际输出，你贴原文）。
- 最后 8 秒日志里应能看到：
  - `[Chat] 配置: 未配置，等待手机蓝牙配网`
  - 没有 `PSRAM 分配失败`、`Guru Meditation`、反复重启。

**如果报错**：
- `the port is busy or doesn't exist` → 板子没插好或线有问题，检查 `ls -l /dev/cu.*`。
- `启动分区: ota_0 (小智)` → 当前启动的是旧版固件，脚本会拒绝操作并提示运行 `python3 tools/boot_switch.py wake --apply`。**不要自己运行它**，把原文贴给我。
- `警告: 无法从 otadata 解析出有效启动分区` → **不要自己改命令**，把原文贴给我。

**汇报**：
- 贴编译字节数那一行（`Sketch uses ... bytes`）。
- 贴校验启动分区那一段（`== 校验启动分区 (只读) ==` 到下一个 `==` 之间）。
- 贴烧录阶段的开始和结束标志（至少包括 `== 烧录到 ota_1 ...` 和写完后的校验消息）。
- 贴最后 8 秒日志里所有 `[Chat]`、`[Wake]`、`Guru`、`PSRAM` 相关的行。

## 任务 2：蓝牙配网

**步骤**：
1. 打开网页（Chrome 或 Edge）：
   ```
   http://localhost:8765/ble_dashboard.html
   ```

2. 点右上角「连接开发板蓝牙」，在系统弹窗里选 `Korvo-刘航成&夏工`（**不需要输入密码**，固件没有设置任何 BLE 安全配对）。

3. 在网页的「板载语音对话·蓝牙配网」面板里填写：
   - **Wi-Fi 名称**：你当前热点的 SSID（例如 `iPhone`）
   - **Wi-Fi 密码**：热点密码（汇报时写成 `***`）
   - **服务地址**：`http://172.20.10.2:8787`（电脑的 IP，用 `ipconfig getifaddr en0` 确认，**必须是 `http://`，不是 `https://`**）
   - 点「写入开发板」。

4. 观察网页顶部的状态标签（在配网面板最上面，写着「状态：...」那一行）：
   - 写入前：`未配置`（或 `状态：未知(需先连接蓝牙)`）
   - 写入后：应该从 `正在连接 Wi-Fi…` 变成 `在线·正在听`

5. 如果一直停在 `正在连接 Wi-Fi…`，在另一个终端运行 `./flash.sh --log-only` 抓串口日志（**注意它会复位板子**），看日志里的报错：
   ```bash
   cd /Users/hancg/Desktop/hackathon
   ./flash.sh --log-only
   ```
   把所有 `[Chat]` 开头的行贴给我，包括 `[Chat] 连接 Wi-Fi:`、`[Chat] Wi-Fi 已连接 IP=...`、`[Chat] 错误: ...`。

**汇报**：
- 网页状态标签最终显示什么（`在线·正在听` 还是 `正在连接 Wi-Fi…`）？
- 如果配网成功，板子的 IP 是多少（日志里的 `[Chat] Wi-Fi 已连接 IP=...`）？
- 如果失败，贴日志里的 `[Chat] 错误: ...` 原文（Wi-Fi 密码写成 `***`，但服务地址的 IP 保留，我需要它判断问题）。

## 任务 3：语音对话测试

**前置条件**：
- 配网成功，网页显示 `在线·正在听`。
- 中转服务 `python3 server.py` 仍在运行（终端 A）。
- **断开蓝牙**（ESP32 的射频是共用的，同时开蓝牙和 Wi-Fi 可能让蓝牙变卡）。

**步骤**：
1. 对着板子说：**"小夜，开始守夜"**

2. **你没法替我开口说话，所以这一步需要和用户配合**：
   a. 先在后台开 90 秒串口抓取（它会先复位板子，板子会用 NVS 里的配置自动重连 Wi-Fi，约需几秒）：
      `LOG_SECONDS=90 ./flash.sh --log-only > "$TMPDIR/board.log" 2>&1 &`
   b. 然后明确告诉用户："现在请等 15 秒，再对着板子说：小夜，开始守夜。"
   c. 用户说完后，读 `$TMPDIR/board.log`，不要等 90 秒结束才读，但要确认抓取已结束再汇报完整日志。

3. 观察三个地方：
   - **板子喇叭**：向用户询问播了什么声音？云端合成的清晰女声，还是板载离线蜂鸣音？
   - **终端 A（中转服务日志）**：看到 `[ASR]`、`[Reply]`、`[Time]` 行了吗？贴出来。
   - **板子日志**（来自上面的 board.log）：看 `[Chat] 开始说话`、`[Chat] 说完了 X.XX 秒，上传`、`[Chat] POST NNNNN 字节 -> HTTP 200`、`[Wake] Night watch started` 这几行。

4. 向用户询问：从说完到听到回复，大约等了多少秒（真实体验时间，不是日志里的数字）。

**汇报**：
- 板子喇叭播了什么声音（向用户询问，因为你自己没有耳朵）？
- 中转服务日志的 `[ASR]` `[Reply]` `[Time]` 行（ASR 和 TTS 耗时是关键）。
- 板子日志的 `[Chat] 开始说话`、`[Chat] 说完了 ...`、`[Chat] POST ... -> HTTP ...`、`[Wake] Night watch started` 行。
  - **如果日志里完全没有 `[Chat] 开始说话` 这一行，说明说话检测没有触发**，汇报时明确说这一点，并把整个 board.log 都贴给我（包括 `[Chat] 配置:` 那些初始化日志）。
- 从说完到听到回复，用户实际等了多少秒（真实体验时间）？

## 任务 4：已知问题排查

**如果任务 3 遇到以下情况**：

1. **板子把自己的回复又听进去了，自己触发了第二次识别**：
   - 表现：说完一句话，板子回复后，又自己触发一次录音和上传。
   - 原因：喇叭和麦克风在同一块板上，回声抑制不够。
   - 汇报：告诉我这个现象，以及中转服务日志里连续两次 `[ASR]` 的内容（第二次识别到的是不是回复的文本）。

2. **说话检测太灵敏（被环境音触发）或太迟钝（听不到你）**：
   - 汇报：描述具体表现（例如"我说话它不录""风扇声让它一直录"），以及你说话时离麦克风多远、环境噪音大不大。

3. **Wi-Fi 和蓝牙同时开导致蓝牙卡顿或掉线**：
   - 汇报：配网过程中有没有卡顿、断连、重连？
