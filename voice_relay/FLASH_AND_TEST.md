# 板子烧录与测试流程

中转服务已验证通过（局域网连通性、追问窗口、TTS 熔断、记梦写入）。下面是烧录固件并完成首次配网测试的步骤。

---

## 前置条件

1. **板子物理连接**：
   - USB 线插在板子**左边那个口**（CH9102F，负责下载和串口日志）。
   - 线是**数据线**，不是只能充电的线。
   - 板子上电（插上去通常就会自己上电）。

2. **中转服务已启动**：
   ```bash
   cd /Users/hancg/Desktop/hackathon/voice_relay
   python3 server.py
   ```
   保持运行在一个终端（终端 A）。

3. **网页服务已启动**（通常已经在后台）：
   ```bash
   cd /Users/hancg/Desktop/hackathon
   python3 -m http.server 8765
   ```

---

## 步骤 1：烧录固件

在另一个终端（终端 B）执行：
```bash
cd /Users/hancg/Desktop/hackathon
./flash.sh
```

**它会做三件事**：
1. 编译（已经编译过的话会很快）
2. **校验当前启动分区**（只读，不写 Flash）- 确认板子启动的是 ota_1
3. **烧录到 0x730000**（写 ota_1）- 约 2.6 MB
4. 抓 8 秒启动日志

**预期输出**：
- `== 编译 ==` 下面应显示 `Sketch uses 2743427 bytes (65%)`
- `== 校验启动分区 (只读) ==` 下面应显示 `启动分区: ota_1 (Wake)  OK`
- `== 烧录到 ota_1 (0x730000)，不会触碰 0x330000 / 0x010000 ==` 下面有进度条，写完应显示 `Hash of data verified.`（这行是 esptool 的原文，我没在本次会话里亲眼见过，以实际输出为准）
- 最后 8 秒日志里应能看到：
  - `[Chat] 配置: 未配置，等待手机蓝牙配网`
  - 没有 `PSRAM 分配失败`、`Guru Meditation`、反复重启

**如果报错**：
- `the port is busy or doesn't exist` → 板子没插好或线有问题。
- `无法解析出有效启动分区` → **不要自己改命令**，把原文贴给我。
- 写入中断、Hash 校验失败 → 可能要重试，或者线不稳定。

---

## 步骤 2：蓝牙配网

1. **打开网页**（Chrome 或 Edge）：
   ```
   http://localhost:8765/ble_dashboard.html
   ```

2. **连接蓝牙**：
   - 点右上角「连接开发板蓝牙」
   - 在系统弹窗里选 `Korvo-刘航成&夏工`
   - 不需要输入配对密码（固件没有设置任何 BLE 安全配对，是明文连接）

3. **填配网表单**（在网页的「板载语音对话 · 蓝牙配网」卡片里）：
   - **Wi-Fi 名称**：你当前热点的 SSID（例如 `iPhone`）
   - **Wi-Fi 密码**：热点密码（例如 `pw123456`）
   - **服务地址**：`http://172.20.10.2:8787`（电脑的 IP，用 `ipconfig getifaddr en0` 确认）
     - 注意：**必须是 `http://`**，不能是 `https://`
     - IP 是**电脑的 IP**，不是 `127.0.0.1`（板子要能访问到）
   - 点「写入开发板」

4. **观察网页右上角状态**（在「板载语音对话·蓝牙配网」面板顶部的状态标签）：
   - 写入前：`未配置`（或 `状态：未知(需先连接蓝牙)`，取决于蓝牙是否连接）
   - 写入后：应该从 `正在连接 Wi-Fi…` 变成 `在线·正在听`
   - 如果一直停在 `正在连接 Wi-Fi…`，检查：
     - Wi-Fi 密码对不对
     - 服务地址的 IP 是不是电脑的 IP
     - 板子和电脑是不是在同一个网络（同一个热点）

5. **看日志确认**（终端 B，运行 `./flash.sh --log-only` 抓日志。注意它会先复位板子，所以只能抓到复位之后的日志，复位后板子会用 NVS 里保存的配置自动联网）：
   ```
   [Chat] 配置: 已有，将联网
   [Chat] 连接 Wi-Fi: <你的SSID>
   [Chat] Wi-Fi 已连接 IP=<板子的IP>
   ```
   写入配置那一刻的日志（`[Chat] 已保存配置: ssid=... server=...`）只会在写入时打印一次，用 `--log-only` 抓不到，因为它会复位板子。想看到它，需要在写入配置时用串口监视器一直开着。

## 步骤 3：语音对话测试

对着板子说：**"小夜，开始守夜"**

**观察三个地方**：

1. **板子喇叭**：
   - 如果 TTS 可用：应该播放云端合成的回复「好的，开始守夜，晚安。」
   - 如果 TTS 熔断（当前很可能）：播放板载离线语音「晚安，开始守夜」（女声，稍显机械）

2. **终端 A（中转服务日志）**：
   ```
   [ASR] '小夜，开始守夜。'  (18.0s)
   [Reply] '好的，开始守夜,晚安。' cmd='N:1'
   [TTS 失败] RuntimeError: TTS 熔断中，还剩 XX 秒
   [Time] ASR 18.0s + TTS 0.0s = 共 18.0s
   ```
   - 如果看到 `[ASR]` 和 `[Reply]`，说明识别成功了
   - `N:1` 是「开始守夜」指令，板子会执行

3. **板子日志**（需要串口监视器一直开着；`flash.sh --log-only` 会复位板子，抓不到你说话时的日志）：
   ```
   [Chat] 开始说话
   [Chat] 说完了 X.XX 秒，上传
   [Chat] POST NNNNN 字节 -> HTTP 200
   [Wake] Night watch started
   ```
   最后一行 `[Wake] Night watch started` 就是"开始守夜"指令被板子真正执行的证据。固件对 N:1/N:2 指令没有单独打印，所以看这一行，以及屏幕是否熄灭。

## 已知限制（需要真机验证）

1. **说话检测阈值**：
   - 我用合成音频测试过，真实麦克风的电平我没见过。
   - 如果太灵敏（被环境音触发）或太迟钝（听不到你），阈值在 `display_name/speech_detect.h` 顶部，可以调。

2. **回放会不会被麦克风听到**：
   - 我在播放期间和之后 700 毫秒让板子"装聋"，但喇叭和麦克风在同一块板上，回声强度只能实测。
   - 如果板子把自己的回复又听进去了，表现是：说完一句话后，板子又自己触发一次识别。

3. **Wi-Fi 和蓝牙同时工作**：
   - ESP32 的射频是共用的，同时开可能让蓝牙变卡或掉线。
   - 测试时注意：配网完成后断开蓝牙，再测语音对话。

4. **唤醒词实际在服务端判断**：
   - 板子会把每一句话都上传，由服务端丢弃没有唤醒词的。
   - 也就是说你周围任何人说话都会被上传到云端识别，只是不回应。
   - 演示时要如实讲清楚，不要说成"本地唤醒"。

## 如果 TTS 一直不可用

当前 `tts-1` 模型一直 429，服务端已经有熔断和降级（板子用离线语音确认）。如果想试试备用模型：

```bash
cd /Users/hancg/Desktop/hackathon/voice_relay
python3 try_alt_tts.py qwen3-tts-flash     # 探测清单里有这个模型
python3 try_alt_tts.py speech-1.5          # 以及这个
python3 try_alt_tts.py tts-1-hd alloy      # 也可以指定音色
```

注意：这个脚本我只做过语法检查，没有真正运行过（沙箱不能联网）。默认用 `.env` 里的 `TTS_VOICE` 请求，不同模型支持的音色名可能不同；如果某个模型报"不支持的音色"，用第二个参数换音色名。

如果成功生成了 WAV 并且你听着是清晰的中文，就在 `.env` 里改 `TTS_MODEL=...`（以及可能需要的 `TTS_VOICE=...`），重启 `server.py`。
